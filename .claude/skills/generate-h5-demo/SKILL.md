# 生產活動 Demo

目標是把一個已經定義好機制的活動點子，快速變成一個「可以點來點去」的靜態網頁，讓團隊在真的投入開發資源前，用畫面驗證整個玩法迴圈順不順、卡關的地方好不好懂。這不是最終產品——用假資料/記憶體 state 模擬就好，重點是流程能走通、視覺跟現有網站一致，不是動畫和美術要做到位。

## 前置：確認機制細節

產生 demo 前，先確認以下幾件事（如果點子是從 `plan-h5-activity` 產出的企劃書拿到的，這些通常已經講清楚了，不用重問）：
- 核心迴圈：玩家做什麼 → 換到什麼資源（代幣/積分/道具）→ 怎麼兌換獎勵
- 有沒有里程碑／進度條，門檻是什麼
- 有沒有小遊戲環節，還是純任務清單
- 特殊機制（每日上限、二次確認、連勝挑戰、邀請碼…）要不要體現在 demo 裡，還是先簡化掉

不確定的地方就用最簡化的假設先做，並跟使用者說明簡化了什麼、為什麼簡化。

## 沿用專案既有資源

動手前先讀這幾個檔案，盡量重用而不是重新發明一套視覺語言：
- `css/style.css`：既有的顏色變數、卡片/按鈕/彈窗樣式
- `js/common.js`：`escapeHtml`、`tagChip`、`openModal`/`closeModal` 等共用函式，以及 `GOAL_TAGS`/`MECHANISM_TAGS` 等標籤定義
- `generate.html`／`ideas.html`：既有頁面的排版與 modal 彈窗寫法

新 demo 的排版、按鈕、彈窗風格要跟這幾個既有頁面一致，這樣團隊看 demo 時不會被「這是另一套風格」分心，能專注在玩法本身。

## 產出結構

在 `demo/<活動代稱>/` 底下建立：
- `index.html`：demo 主頁，引入本專案的 `css/style.css`，機制特有的視覺（小遊戲畫面、里程碑進度條）用最小的內聯或獨立 CSS 補充
- `demo.js`：純前端邏輯，用一個記憶體內的 state 物件模擬玩家進度（代幣數、任務完成狀態、里程碑領取狀態）；重整頁面預設會重置，除非這個活動的機制重點就是「進度要保留」，那才用 localStorage 存

如果核心玩法是一個小遊戲（點擊消除、拖曳、倒數計時型…），優先用最簡單能表達手感的做法（純 CSS/DOM 操作即可），不需要真的做 canvas 遊戲引擎——目標是讓人理解「玩起來是這種感覺」，不是做出正式遊戲。

## 必須還原的畫面狀態

即使是簡化 demo，至少要能展示：
1. 主頁：任務/小遊戲入口＋目前代幣/進度顯示
2. 任務清單彈窗：可領取／未完成／已領取三種狀態
3. 里程碑列表：鎖住／可領取／已領取三態（如果活動有里程碑機制）
4. 領獎彈窗：點擊兌換後的確認與成功回饋
5. 若機制涉及小遊戲：至少要有入口 → 遊玩 → 結算的最小可玩流程

這五個狀態涵蓋了團隊過去工單裡最常見的驗收畫面（見 `.claude/knowledge/h5-activities/kpi-and-qa-reference.md` 的「其他通用 UI 細節提醒」），展示這些通常就足以讓人評估整個活動流程順不順。

## 完成後

用瀏覽器預覽工具實際點過一次核心流程（進任務→完成→領獎；如果有小遊戲，玩一輪），確認沒有壞掉的按鈕或報錯。跟使用者回報時說明「這是簡化過的地方」以及「這份 demo 目的是驗證流程，不是最終美術/動畫」，避免對方誤以為這就是成品標準。
