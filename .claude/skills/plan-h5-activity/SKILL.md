# 規劃 H5 活動

傳說對決營運團隊發想新活動時，思考順序固定是「先目的、後限制、才輪到機制」。這不是形式主義：目的決定要用哪種機制家族，限制決定這個機制實際做不做得出來。跳過這兩步直接端出一個好玩的機制，通常會在後面被打回票，因為根本沒對齊需求。

## 步驟 1：確認目的

問使用者這次活動要達成什麼目的，答案要落在：
- 六大分類：拉新／回流／留存／付費／版本導流／品牌口碑
- 或本站 `js/common.js` 定義的四個 `GOAL_TAGS`：提升主要模式時長／提升其他模式時長／提升非對局在線時長／提升登入率

如果使用者的原始需求裡已經講清楚（例如「這次連假想拉活躍」），直接複述確認就好，不用硬問一輪；只有真的沒講或講得模糊時才追問。

## 步驟 2：確認現有限制

問使用者：
- 檔期／時間點（連假、版本更新、IP聯動、電競賽事、週年慶、異業合作、無特定檔期）
- 開發時程與資源（有沒有時程壓力、是否要標「低開發成本」）
- 有沒有既定 IP／聯名／異業合作資源可以用

## 步驟 3：呼叫 learn-insights 撈洞察佐證

用 Skill 工具呼叫 `learn-insights`（模式B：檢索），把步驟 1、2 確認好的目的與限制當關鍵字，請它從 `.claude/knowledge/h5-activities/` 篩出真正相關的歷史案例、可複用技巧、參與率/完成率量級。**不要自己整包讀知識庫資料夾**，把篩選這一步交給 `learn-insights` 做，這是避免每次規劃都把大量無關資料塞進對話的關鍵設計（對應知識庫的 RAG 檢索層）。

## 步驟 4：判斷能不能套用既有引擎

根據 `learn-insights` 回傳的洞察，判斷這次的目的＋限制組合能不能直接沿用某個已驗證過的機制引擎。能套用的話開發成本會低很多，要主動點出「這個可以直接沿用哪個引擎」，而不是預設每次都要全新設計機制。如果現有引擎都不合適，才發想新機制，但仍要參考同類機制的量級與教訓。

## 步驟 5：產出企劃書

綜合以上，輸出一份企劃書，結構固定如下：

```
# 活動名稱（暫定）

## 目的與檔期
（目的分類、GOAL_TAGS、檔期/限制）

## 機制設計
（核心迴圈：怎麼開始→怎麼參與→怎麼獲得資源→怎麼兌換；套用哪個既有引擎或為何需要新機制）

## 參考案例與洞察
（引用 learn-insights 回傳的歷史案例卡與可複用技巧，附案例卡來源檔名）

## 預期成效
（參與率／完成率的預期量級，並註明類比哪個歷史案例；「參與」「完成」動作各自的定義）

## 標籤
mechanismTags / purposeTags / specialTags（對應 js/common.js 的標籤定義）

## 待確認事項
（規則模糊處列成問題清單，不要自己假設答案）
```

這份企劃書要能直接交給 `generate-h5-demo` 技能轉成 demo，也方便使用者複製整理進正式工單，或貼到「我有活動靈感」頁面（欄位可對應 `js/mock-data.js` 的 `MOCK_IDEAS`：title、description、purposeTags、inspirationRef）。

## 例外

如果使用者明確說「我已經決定目的和限制了，直接跳到機制」，就尊重他們，不要硬性重複問一輪——這個流程是預設的思考順序，不是不能跳過的關卡。
