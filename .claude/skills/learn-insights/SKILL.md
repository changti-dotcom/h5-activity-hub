# 學習洞察

這是整個活動規劃工具的知識萃取站，負責兩種模式：吸收新資料（模式A）、檢索既有知識（模式B）。

## 模式 A：吸收新工單（使用者主動提供新資料時）

1. 讀完使用者提供的工單/簡報/成效數據全文。檔案很大時先用 jq/python 探測結構再分段讀，或委派給 subagent 讀完整份再摘要回來，避免把原始全文一次塞進主對話。
2. **不要把工單原文或大段敘事摘要直接寫進知識庫**——工單裡有大量流程雜訊（誰指派給誰、狀態變更、來回討論），對未來發想沒用。只萃取成案例卡，固定欄位：活動名稱／上線時間／原始目標／機制設計重點（一句話）／阻礙與解法（工單裡最有價值但最容易被忽略的部分）／參與率／完成率／備註。
3. 判斷這個活動屬於哪個「機制引擎」（心理測驗、經營模擬、劇情回顧、陣營競賽、多合一小遊戲、任務養成、解謎小遊戲、捐獻排行榜文化包裝…）：
   - 如果 `.claude/knowledge/h5-activities/cases/` 底下已經有同引擎的檔案（例如 `food-stand-engine.md`），把新案例卡加進去同一個檔案，不要為同引擎的活動分散開新檔案。
   - 如果是全新的機制引擎，開一個新檔案，檔名用引擎的英文/拼音簡稱。
4. 更新 `.claude/knowledge/h5-activities/index.md`：加一列（活動名稱、案例卡檔案、機制類型、原始目的、關鍵字標籤）。
5. 如果這份新工單揭露了「跨案例才看得出來」的規律（例如某個技巧在好幾個引擎都出現、或某個機制類型的量級因為新樣本要重新計算），更新 `mechanism-insights.md` 的對應段落。
6. 如果這份工單提到 KPI/Data Request/合規/QA 的通用規則，且 `kpi-and-qa-reference.md` 還沒記錄，補進去；只是重複既有內容就不用動。
7. **做完務必用 git commit 這幾個異動的檔案**（不要只留在工作目錄），避免環境重置後知識庫又消失。

## 模式 B：檢索既有洞察（被 `plan-h5-activity` 呼叫、或使用者直接問「過去有沒有類似案例」）

**這是知識庫的 RAG 檢索層，關鍵原則是「先過濾再讀」，不要把整個知識庫塞進對話：**

1. 先 Read `.claude/knowledge/h5-activities/index.md`（唯一預設每次都完整讀的檔案，本身很小）。
2. 根據目的/機制關鍵字（例如「拉新」「心理測驗」「經營模擬」），對照 index.md 的「原始目的」與「關鍵字標籤」欄位篩出候選列；也可以用 Grep 在 `cases/` 目錄下搜尋關鍵字確認命中範圍。
3. 只 Read 篩選後命中的少數案例卡檔案，以及 `mechanism-insights.md` 裡對應機制類型的段落——不要整包讀 `cases/` 底下所有檔案，也不要每次都讀 `kpi-and-qa-reference.md`（除非使用者明確要 KPI/合規細節）。
4. 回傳時附上引用來源（案例卡檔名），讓使用者/`plan-h5-activity` 知道這個洞察是從哪個歷史案例來的，方便回頭查證。

## 為什麼要分兩個模式而不是一個大流程

模式 A（累積知識）和模式 B（篩選檢索）是完全不同方向的操作——A 是寫入、由人主動觸發，B 是讀取、由規劃流程自動觸發且頻率高很多。分開描述可以避免每次檢索都誤觸發成一次「重新學習」的動作，也讓知識庫的寫入頻率（同事丟新工單時）跟讀取頻率（每次規劃活動時）各自獨立運作。

## 輸出格式

模式 A 完成後，簡短回報：新增/更新了哪些檔案、案例卡的核心內容摘要（一兩句話），不用整段貼出來。
模式 B 完成後，直接把篩選到的洞察整理成重點條列給使用者/`plan-h5-activity` 用，附案例卡來源檔名。
