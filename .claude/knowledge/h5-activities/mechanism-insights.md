# 機制歸納與可複用技巧（跨案例綜合，樣本數還小，隨資料增加要重新算）

## 依機制分類的參與率/完成率量級

| 機制類型 | 樣本（見 cases/） | 參與率量級 | 完成率量級 | 解讀 |
|---|---|---|---|---|
| 劇情回顧（週年慶） | skin-review-engine.md | ~44–49% | ~27–48% | 門檻極低（看完就能領），參與率與完成率同時最高，適合品牌口碑型活動 |
| 心理測驗 | find-your-soul-engine.md | ~42% | ~33% | 低門檻、高完成，適合拉新/短期衝聲量 |
| 經營模擬 | food-stand-engine.md | ~31% | ~9% | 完成率天生低，長線經營玩家易半途而廢，目的是留存要看回訪別看完成率 |
| 反應操作 | clash-battle.md | ~31% | ~11% | 吸引力夠但衝到終點門檻偏高 |
| 任務養成 | candle-donation.md、shower-puzzle.md | ~20–28% | ~9–19% | 有沒有掛在大檔期（節慶）明顯影響參與率高低 |
| 陣營競賽 | territory-war.md | ~23% | ~5% | 門檻高（需持續多日操作），完成率天生很低，別用它衝完成率類 KPI |

給建議時主動引用這張表：KPI 重點是完成率/獎勵發放效率 → 優先推心理測驗或劇情回顧；重點是拉長每日回訪天數 → 可用經營模擬或陣營競賽，但要提醒完成率預期會低。

## 特殊關鍵指標對照表（除參與率/完成率外，依機制額外看的指標）

不是每個點子都要求一個特殊指標，只有機制本身有獨特資源/行為時才需要：

| 機制特徵 | 特殊指標 | 範例 |
|---|---|---|
| 可直接投入遊戲內真實貨幣 | 貨幣消耗量／占全服存量比例 | candle-donation.md：消耗17億金幣，約全服存量3% |
| 一次活動內含多款小遊戲合輯 | 跨小遊戲滲透率 | carnival-engine.md |
| 拚手速/拚數值累積型 | 人均產出量 | clash-battle.md |
| 需要邀請/找朋友才能完成 | 邀請成功率／K-factor | candle-donation.md（好友流失天數綁定） |
| 經營模擬/長線養成型 | 平均每日回訪操作次數 | food-stand-engine.md |
| 解謎/連勝挑戰類 | push-your-luck 放棄率 vs 續玩率 | summer-fest-streak.md |

## 可複用的設計技巧庫（依觸發情境查找）

- **多合一小遊戲的雙軌代幣**：消耗型代幣（玩小遊戲賺）＋不消耗入場資格（任務/分享/邀請換到）＋看廣告等免消耗管道，兼顧輕重度玩家（carnival-engine.md、summer-fest-streak.md）
- **連勝挑戰 push-your-luck**：小遊戲過關後問「帶走現有代幣」還是「賭一把拚更高連勝」，失敗歸零，加深度不加複雜度（summer-fest-streak.md）
- **保證可解＋隨機感掉落演算法**：後台準備保證路徑零件，混雜雜訊零件打散，確保前N個掉落內出現，用於隨機解謎小遊戲（shower-puzzle.md）
- **里程碑四態視覺**：未達標鎖住／已達標未到開放時間／已到時間未達標／已領取，是所有代幣型活動的 UI 規範範本（candle-donation.md）
- **邀請機制綁定好友流失天數**：越久沒登入的好友，互動可得越多代幣，同時做到社交裂變＋老玩家召回（candle-donation.md）
- **一般代幣來源 vs 即時代幣來源分資料流**：任務型（有延遲）與即時互動型（API/邀請碼）要分開設計信任等級與提示（candle-donation.md）
- **收銀台式收益封頂**：收益存進容器、滿24hr封頂要手動收，比每日任務更輕量地逼玩家每天回來（food-stand-engine.md）
- **收集敘事驅動留存**：獎勵預算有限時，可以靠「收集不同隨機內容」的好奇心而非代幣本身驅動重複遊玩（travel-diary.md）
- **心理測驗萬用引擎**：多問題少變因降低後端負擔；換皮選題要用優缺點比較表（擴散力 vs IP/檔期關聯度）（find-your-soul-engine.md）
- **文化敘事包裝排行榜**：求籤/爐主/施主稱謂把冷冰冰的數值排行榜變成有溫度的社交榮譽感（candle-donation.md）
- **異業合作虛實混合大獎**：遊戲內效果/道具＋真實商品限量抽獎，需另外規劃實體物流（shower-puzzle.md）
- **引擎複用優先於全新開發**：心理測驗、光明燈、經營模擬、劇情回顧都已被驗證可換皮重複使用，發想新點子先問能不能套現有引擎
- **上線前數值試算＋上線後 forecast vs actual 校準**：陣營競賽/任何有精算需求的活動都該延續這套流程（territory-war.md，誤差僅2.82%）
- **大改版是常態**：保留舊方案（archived）紀錄供之後參考，不是浪費（summer-fest-streak.md）
